# 原生运控与 SDK 架构计划

本轮按 Unitree 公开 SDK 与仿真桥接的分工继续开发：独立控制客户端、统一类型消息、原生机器人端、设备执行后端。用户追加要求为全身31关节500Hz执行。现有舞蹈Actor保持50Hz，执行层在两次策略更新之间保持目标。研究、实现和交叉审查由三个单元与主代理共同完成，不启动训练、不录制视频、不操作真实设备。

## 公开依据

- [Unitree SDK2](https://github.com/unitreerobotics/unitree_sdk2) 的类型化 ChannelFactory、Publisher、Subscriber 与低层控制例程；部分例程采用2000微秒周期。
- [Unitree MuJoCo](https://github.com/unitreerobotics/unitree_mujoco) 的独立C++/Python仿真DDS端，控制客户端复用消息。
- [Universal Robots 接口](https://www.universal-robots.com/articles/ur/interface-communication/remote-control-via-tcpip/) 中e-Series采用500Hz接口。
- [Franka FCI](https://frankarobotics.github.io/docs/doc/libfranka/docs/overview.html) 采用1kHz实时控制。工业产品并非统一频率；本工程明确选择500Hz，并单独验证时延、带宽和故障行为。

公开代码没有完整呈现厂商机器人内部固件。本工程参考公开架构与接口习惯，不宣称复刻未公开固件，也不将软件循环频率写成工业认证或实机硬实时保证。

## 交叉质询与共识

| 质询 | 决策 |
|---|---|
| DDS应直接进入2kHz CAN循环吗 | 独立原生DDS机器人端，类型消息经有界缓存与原生设备IPC连接。网络发现与可靠应答不进入CAN调度关键路径。 |
| 只给现有JSON C ABI加C++外壳够吗 | 不够。抽取共享类型端点，C++ SDK与机器人端直接收发生成类型；Python C ABI保持兼容。原生高频路径不转JSON。 |
| 仿真是否仍加载Actor | 移除机器人端对PolicyBundle/ONNX的依赖。场景初始化只包含机器人资产、profile、qpos/qvel；参考评估在独立工具中进行。 |
| 是否只把循环常量改成500 | 全31电机命令调度、反馈轮询和原生聚合状态目标统一500Hz；保留2kHz错相传输。逐关节计数、周期和截止时间必须可核查。 |
| 原生状态由50变500Hz会影响什么 | 移除“源状态最多落后5个序号”的频率假设，改为已发布序号/时间缓存。Actor按20ms选择状态，不能因收到500Hz状态而跑成500Hz。 |
| 总线是否够用 | 实际协议为标准ID、8字节CAN FD+BRS。按每帧64个仲裁速率bit加128个数据速率bit保守预算，每个电机每周期一发一收。校验每总线负载与500微秒槽位预算；核验实际内核链路速率和FD模式。 |
| 500Hz是否包括仿真物理 | 不包括。用户明确要求物理始终200Hz、关节目标下发500Hz、Actor50Hz。采用独立时钟，物理每5ms更新一次，执行器目标每2ms更新一次；不伪造传感器采样。 |
| 500Hz发布是否等于500Hz独立传感器采样 | 不等于。保留每个电机和IMU的原始采样时间；不能反复发布旧测量冒充更新。 |
| 是否放松既有保护 | 保留命令因果来源、控制权、重放、10ms执行反馈与30ms IMU限制、机构映射、量化、完整PD力矩和原生退出报告。 |

## 实施单元

1. SDK单元：共享类型端点、Unitree风格C++ Channel/Client、安装头文件、库与CMake配置，Python传输回归。
2. 原生运控单元：独立C++执行进程、公共设备接口、管理状态机、硬件二进制IPC及IMU适配、权限/来源/时间和退出检查。
3. 主代理：全31电机500Hz调度、带宽与链路预检、离线配置编译；原生MuJoCo后端与独立场景、50Hz策略采样、迁移文档与完整策略验收。
4. 验证单元：安装后外部C++客户端、Python/ROS 2互通、真实MuJoCo、假native/IMU、故障注入、500Hz计数与独立发行；交叉审查其他单元。

先落公共Backend接口和类型API，再并行实施。各单元由其他成员复核；明确的严重问题修复并回归后才能交付。

## 验收要求

- 既有250项测试保留；增加C++类型API与原生执行状态机测试，真实独立进程收发四种消息。
- 外部工程仅使用安装后的头文件/CMake库编译客户端；核对C++、Python与ROS 2的字段、整数、数组与状态语义。
- 原生机器人端不依赖Python、ONNX或训练代码；用ELF依赖、进程映射和隔离运行检查。仿真场景可在没有策略资产时独立启动。
- 对31电机在完整槽位周期逐项计数500Hz；源状态缓存按真实时间判定；不足带宽、错误FD/bitrate、旧反馈、未知序号和不匹配profile必须拒绝。
- 原生硬件路径使用实际二进制IPC与假设备测试，不打开CAN。控制进程崩溃、诊断读者暂停、来源重放、传感器断流、误启用和退出故障均须覆盖。
- 原生MuJoCo先验证500Hz指令与200Hz物理计数，再使用独立Actor执行完整225.66秒参考。首次失败、完整执行和软件验收分开记录。
- 源码搬迁、SDK/native库安装、相对资产路径、许可证和生成清单检查通过。.reference、outputs和父项目不作为运行依赖。
- Jetson ARM64、USB适配器时延、实际电机响应及总线测量保留实机验收项，不以开发机测试替代。
